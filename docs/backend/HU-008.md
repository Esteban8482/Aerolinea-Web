## Contrato HTTP para frontend

OpenAPI generado por drf-spectacular es el contrato ejecutable: `/api/schema/` y
`/api/docs/` en desarrollo/pruebas. Las rutas siguientes comienzan por `/api/v1/auth/`.
Todas admiten JSON; se rechazan campos desconocidos, identificadores ambiguos y campos
privilegiados. No se publican correos, perfil, tokens ni identificadores de sesión.

| Método y ruta | Entrada | Éxito |
|---|---|---|
| GET `csrf/` (HU-007) | Sin cuerpo | 200 `{"csrf_token":"…"}` y cookie CSRF |
| POST `login/` | email **o** root_id, password | 200, estado de sesión y cookies rotadas |
| GET `session/` | Sin cuerpo | 200, estado mínimo; nunca renueva actividad |
| POST `session/activity/` | `{}` | 200, renueva 30 min si el intervalo lo permite |
| POST `logout/` | `{}` | 200 `{"status":"logged_out"}`; idempotente |
| POST `password-recovery/` | email | 202 `{"status":"requested"}` uniforme |
| POST `password-reset/` | token, password, password_confirmation | 200 `{"status":"password_reset"}` |

Login de CLIENTE/ADMINISTRADOR:

```json
{"email":"persona@example.invalid","password":"CONTRASEÑA-SINTÉTICA"}
```

Login ROOT (ID sensible a mayúsculas, espacios exteriores eliminados):

```json
{"root_id":"root-de-prueba","password":"CONTRASEÑA-SINTÉTICA"}
```

No enviar ambos identificadores, `username`, rol, verificación, saldo, staff o superuser.
Correo se recorta y normaliza a minúsculas; la contraseña conserva espacios y Unicode
exactos. ROOT con correo asociado sigue autenticándose solo por root_id. No se vincula
ningún permiso de negocio al indicador staff/superuser.

Estado autenticado:

```json
{"authenticated":true,"role":"CLIENTE","is_email_verified":false}
```

Estado visitante, incluida una sesión vencida o invalidada:

```json
{"authenticated":false,"role":null,"is_email_verified":false}
```

Frontend usa rol para presentar opciones, pero cada futura operación debe imponer rol,
propiedad y verificación en backend. El permiso `HasVerifiedEmail` de HU-007 sigue siendo
necesario donde corresponda. No desviar al visitante ni denegar login únicamente porque
`is_email_verified=false`.

Revisión conjunta del 2026-10-21: la actualización de hashes heredados durante login
usa una escritura condicional en `User.check_password` (también async). Si una recuperación
ya cambió la contraseña, no sobrescribe esa credencial y el login antiguo devuelve 401.
Un rehash exitoso cambia el hash al que se ligan recuperaciones pendientes; si un enlace
anterior queda inválido, solicitar otro. Véase [evidencia conjunta](ITERACION-01_REVISION.md).

## Cookies, CSRF y actividad

Sesiones de Django en PostgreSQL, cookie `sessionid` HttpOnly/SameSite=Lax y Secure en
producción. CSRF no se reemplaza por JWT ni por comprobar únicamente el encabezado Origin.

1. GET `csrf/` con cookies; guardar el token devuelto.
2. En todos los POST públicos y autenticados enviar cookie CSRF y `X-CSRFToken`.
3. Login rota identificador de sesión, incluso al reautenticar la misma cuenta, y rota CSRF.
   Después de un 200, **volver a obtener GET csrf/** antes del siguiente POST. El token
   anterior falla con 403 `csrf_failed`.
4. GET `session/` informa estado sin renovarlo; sirve para carga inicial y polling.
5. Tras interacción real del usuario, POST `session/activity/` con `{}`. Frontend agrupa
   eventos y envía como máximo una petición/minuto; no emite latidos automáticos en reposo.
   El servidor exige 60 s desde login o última renovación; antes devuelve 429/Retry-After.
6. En `ahora >= última_actividad + 1800 s` la sesión vence, se revoca y pasa a visitante.
   GET, salud, CSRF, recuperación y demás peticiones no renuevan el plazo. No se revive
   una sesión vencida con actividad. Cada sesión tiene su propio instante en PostgreSQL.
7. Logout revoca la sesión actual y elimina su cookie. Reutilizar la cookie anterior no
   autentica. Una carrera entre logout y la respuesta de actividad devuelve 409
   `session_invalidated`, sin recrear la fila eliminada.

Ejemplo de cliente bajo el mismo origen (proxy Vite `/api` en desarrollo):

```javascript
let csrfToken;
async function refreshCsrf() {
  const data = await fetch('/api/v1/auth/csrf/', {
    credentials: 'same-origin'
  }).then(r => r.json());
  csrfToken = data.csrf_token;
}
await refreshCsrf();
const response = await fetch('/api/v1/auth/login/', {
  method: 'POST', credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json', 'X-CSRFToken': csrfToken },
  body: JSON.stringify(credentials)
});
if (response.ok) await refreshCsrf();
```

No guardar cookies o claves en localStorage ni añadir CORS universal. Un 403 no significa
siempre sesión vencida: distinguir `csrf_failed`, `not_authenticated` y permisos de negocio.
Frontend debe cesar actividad/polling privilegiado al detectar visitante y limpiar su estado.
El backend verifica peticiones válidas; no puede probar que hubo una interacción humana.

## Cuotas, bloqueos y enumeración

**DEC-18:** cinco fallos consecutivos dentro de una ventana móvil de 900 s bloquean el
identificador 900 s. Intentos 1–4: 401 `invalid_credentials`; el quinto: 429 `throttled`.
Durante bloqueo, incluso clave correcta recibe 429 con los segundos restantes; no lo
prolonga ni incrementa los fallos. Éxito o fin del bloqueo reinician el contador. Fallos
fuera de la ventana dejan de contarse. Misma política para ROOT e identificadores inexistentes.

Origen: máximo 30 solicitudes de login/900 s, compartidas entre clientes/workers, incluidas
entradas inválidas con CSRF válido. No se heredan las cuotas de registro de HU-007. Cuenta
se identifica por modo + identificador normalizado y HMAC; origen por IP obtenida mediante
`request_origin`, no mediante el encabezado HTTP Origin. La configuración compartida
`REGISTRATION_TRUSTED_PROXIES` conserva su nombre histórico: se confía en X-Real-IP solo
si REMOTE_ADDR es un peer explícitamente autorizado. El proxy debe sobrescribir la cabecera
y bloquear accesos que lo eludan.

**DEC-19:** recuperación 3/correo/hora, 20/origen/hora, espera mínima 60 s, también para
correos desconocidos/inactivos. Las cuotas de origen se consumen antes de validar datos;
las de correo después de validar formato. Cuotas persisten aunque la operación posterior
falle. La clave HMAC impide guardar correo/IP en claro en contadores.

Las credenciales incorrectas, inexistentes e inactivas tienen el mismo error; AccountBackend
realiza trabajo de hash también para cuentas inexistentes. No se consulta Pwned Passwords
durante login. No se promete indistinguibilidad temporal perfecta en red/base/SMTP; se
evitan la respuesta reveladora y la salida rápida sin hashing. Recuperación no envía SMTP
síncrono, nunca devuelve enlaces y conserva una respuesta 202 uniforme para cuentas inelegibles.

## Recuperación y restablecimiento

Solicitud: `{"email":"persona@example.invalid"}`. En una transacción con bloqueo de usuario
se sustituye la recuperación previa y se crea `PasswordRecovery` con destinatario, estado,
expiración de 30 min y huella HMAC de la versión de contraseña. Cuentas inactivas o sin
contraseña utilizable no reciben enlaces; clientes sin correo verificado sí pueden recuperar.
ROOT usa el correo asociado opcional. **ROOT sin correo no tiene recuperación por este canal**;
no se inventan preguntas, códigos de soporte ni un procedimiento alternativo.

Un procesador separado envía `PASSWORD_RECOVERY_FRONTEND_URL#token=…`. El token está
firmado con propósito `users.HU008.password-recovery.v1`, distinto de verificación; vincula
cuenta y notificación, sin perfil/correo. No se persiste el token utilizable. La huella HMAC
no permite sustituir al firmante ni recuperar la contraseña. Cambiar correo o contraseña,
desactivar la cuenta o emitir otro enlace puede invalidarlo conforme a las comprobaciones.
La vigencia parte de la solicitud, no del envío ni de los reintentos SMTP.

Frontend extrae el fragmento, lo retira inmediatamente con `history.replaceState`, evita
logs/analítica y solicita dos veces la contraseña. No adjuntar token como query o ruta del
backend. GET no consume ni restablece; el usuario confirma mediante POST:

```json
{
  "token":"TOKEN-SINTÉTICO-DEL-CORREO-LOCAL",
  "password":"NUEVA-CONTRASEÑA-SINTÉTICA",
  "password_confirmation":"NUEVA-CONTRASEÑA-SINTÉTICA"
}
```

Se comprueba token/estado antes de llamar al proveedor. Validadores Django y el
[cliente vigente por rango](HU-007_COMPROBACION_CONTRASENAS.md) se ejecutan antes de la
transacción de cambio: mínimo 12, similitud, comunes, numéricas y contraseñas comprometidas;
UTF-8 sin recortar, TLS/padding y espera total 3 s sin reintentos. Un fallo del proveedor
produce 503 `password_check_unavailable`; contraseña anterior y token se conservan.

Luego se bloquean usuario y recuperación en ese orden y se revalidan propósito/vínculo,
estado activo, correo, sustitución, uso, expiración, huella y atributos locales. Solo entonces
se guarda Argon2id, consumo y evento conjuntamente. Dos consumos concurrentes tienen un
único éxito. Un fallo de persistencia revierte contraseña, consumo y auditoría.

**Sesiones después del cambio:** Django compara el hash de autenticación con la contraseña
vigente en la siguiente petición de cada sesión y la invalida, incluida la del solicitante.
No se recorre ni decodifica toda la tabla de sesiones y no se llama update_session_auth_hash.
Puede haber filas de sesiones antiguas hasta su próxima petición o limpieza por vencimiento;
no vuelven a autenticar. Peticiones ya autenticadas y en curso no se deshacen retroactivamente.
No hay login automático ni marca de correo verificado; frontend vuelve a la pantalla de login.

## Errores

Todos usan `{"code":"…","message":"Mensaje en español","details":{}}`; validaciones
incluyen errores de campo en details. Sin contraseña, token, cookie, prefijo/hash o excepciones.

| HTTP | Código | Tratamiento frontend |
|---|---|---|
| 400 | invalid | Revisar campos, combinaciones o confirmación de contraseña |
| 401 | invalid_credentials | Mensaje genérico; no identificar qué credencial falló |
| 403 | csrf_failed | Renovar CSRF y revisar cookie/origen |
| 403 | not_authenticated | Reconsultar estado; solicitar login |
| 429 | throttled | Esperar Retry-After; no reintentar en bucle |
| 400 | recovery_invalid | Enlace alterado, sustituido, de otro propósito o cuenta inelegible; solicitar otro |
| 410 | recovery_expired | Solicitar otro enlace |
| 409 | recovery_used | Enlace ya utilizado; login o nueva recuperación |
| 409 | session_invalidated | Sesión revocada concurrentemente; limpiar estado y pedir login |
| 503 | password_check_unavailable | Conservar formulario y enlace; reintento manual posterior |
| 415 / 500 | unsupported_media_type / internal_error | JSON requerido / error sin detalles sensibles |

## Persistencia, correo y configuración

Nueva migración **users.0005_authentication_sessions_and_recovery**: LoginGuard,
AccountSession (metadatos de actividad, FK a la sesión Django existente), PasswordRecovery
y AuthenticationEvent. No se modifican 0001–0004 ni modelos de HU-007/billetera. Sesiones
anteriores sin metadatos no acreditan actividad y se revocan al usarse; no se inventa una
fecha histórica. El dominio de recuperación permanece separado de EmailVerification.

Se reutilizan AccountBackend, sesiones, errores, validador por rango y cuotas existentes
con ventana parametrizable (el valor por defecto de HU-007 sigue siendo 3600 s). También
la validación de URL de correo; no se cambia su propósito ni se introduce una cola genérica.
AuthenticationEvent conserva actor cuando corresponde, tipo, fecha, recuperación y claves
HMAC de identificador/origen. No replica correo, contraseña, cookie ni token.

Única variable nueva: `PASSWORD_RECOVERY_FRONTEND_URL`, pantalla absoluta sin query,
fragmento o credenciales; HTTPS fuera de DEBUG. Compose la pasa sin modificar `.env`.
Desarrollo usa consola; pruebas/ensayo usan memoria. SMTP, SECRET_KEY, DATABASE_URL,
TEST_DATABASE_URL, cookies y confianza en proxy conservan su configuración documentada.
Parámetros DEC-18/19/20 son constantes comunes versionadas, no secretos ni valores distintos
por worker. Sin dependencias nuevas ni cambios de locks. Se requiere salida HTTPS directa
al proveedor solo al restablecer, no para login/salud.

Desde raíz WSL/Linux, con `.env` existente configurado:

```bash
docker compose up --build -d --wait
docker compose exec -T backend python manage.py migrate --noinput
docker compose exec -T -e PASSWORD_RECOVERY_FRONTEND_URL=http://localhost:5173/restablecer backend python manage.py process_recovery_emails --batch-size 100
```

El último comando usa consola en desarrollo y muestra el enlace: conservar su salida
privada. No usar destinatarios reales en ensayos. Integración programa `process_recovery_emails`
y `process_verification_emails` por separado cada minuto, además de `clearsessions` periódico.
El procesador requiere commit previo, usa skip_locked y lease UUID de 5 min recuperable;
SMTP está fuera de transacción. Reintenta el mismo enlace tras 60,120,240… s hasta máximo
una hora entre intentos, solo mientras siga vigente. No procesa consumidos, sustituidos,
vencidos, inactivos o destinatario cambiado. Un fallo SMTP guarda solo mail_unavailable.
Una caída tras SMTP y antes de sent_at puede duplicar un correo; no duplica el restablecimiento.
La aceptación local no demuestra entrega ni el objetivo de cinco minutos en producción.

## Integración manual y pendientes

Usar cuentas y claves sintéticas, `example.invalid` y correo en memoria/consola. Obtener
CSRF, hacer login con cada identificador admitido, renovar CSRF y consultar sesión. Tras
60 s de interacción hacer POST activity y verificar renovación. Logout y reproducción de
cookie anterior deben dar visitante. Solicitar recuperación, ejecutar el procesador tras
commit, retirar el fragmento del enlace y restablecer por POST; comprobar reutilización,
clave anterior rechazada, nueva admitida, sesiones anteriores invalidadas y correo sin
cambiar de verificación. Expiración de 30 min y bloqueo de 15 min se comprueban con reloj
controlado en pytest, sin esperas reales ni alterar fechas de cuentas de desarrollo.

**Backend:** implementado y verificado en Docker/PostgreSQL 17.11; listo para revisión y
consumo desde frontend. **Frontend:** pendiente. **Integración:** cliente HTTP local
verificado; operación de SMTP/proxy y despliegue pendientes. **HU completa:** no cerrada,
