## Contrato para frontend

**OpenAPI generado por drf-spectacular es la fuente del contrato HTTP.** Incluye campos,
obligatoriedad, formatos, respuestas y cabecera CSRF. Consultar `/api/schema/` o
`/api/docs/` en desarrollo. No se mantiene otra tabla HTTP duplicada en esta guía.

Rutas bajo `/api/v1/auth/`: `csrf/` (GET), `registration-policy/` (GET), `register/` (POST),
`verify-email/` (POST) y `resend-verification/` (POST). El documento sintético está en
`registration-policy/test-document/`; en producción responde 404.

Primero obtener la política vigente. Ejemplo de respuesta de desarrollo:

```json
{
  "reference": "DOCUMENTO-DE-PRUEBA",
  "version": "test-v1",
  "url": "http://localhost:8000/api/v1/auth/registration-policy/test-document/",
  "is_test_document": true
}
```

Mostrar el documento, identificar expresamente que es una prueba y exigir aceptación
activa. Enviar su referencia y versión para detectar un formulario desactualizado.
El servidor valida ambos contra su configuración y persiste **sus propios valores**,
URL y fecha UTC vinculados a la cuenta. No confía en una versión elegida por el cliente.
Un cambio de versión exige mostrar y aceptar nuevamente el documento antes del registro.
No se fabrica consentimiento para cuentas previas ni se redacta una política legal.

Ejemplo sintético de alta JSON sin imagen; todos estos campos son obligatorios:

```json
{
  "email": "persona@example.invalid",
  "username": "viajero",
  "first_name": "Persona",
  "last_name": "De Prueba",
  "document_number": "00123456",
  "birth_date": "1995-06-15",
  "birth_place": "Pereira",
  "billing_address": "Dirección ficticia",
  "gender": "dato de prueba",
  "password": "ejemplo-largo-solo-para-pruebas-2026",
  "accepts_data_policy": true,
  "policy_reference": "DOCUMENTO-DE-PRUEBA",
  "policy_version": "test-v1"
}
```

`document_type` es opcional como en BASE-01; no se inventaron catálogos documentales,
de género, edades mínimas ni otras restricciones personales. El documento es texto y
conserva sus ceros iniciales. Correo se normaliza a minúsculas; documento no es único.

Con imagen usar `multipart/form-data`, mismos campos y archivo `image` opcional. Dejar
que el navegador genere el `Content-Type` con su boundary. Solo JPEG/PNG/WebP reales,
hasta **2 MiB de entrada** y **4096×4096**. Se verifica y recodifica como PNG sin metadatos,
con nombre aleatorio; para animación se conserva el primer fotograma. No se admite una
URL como sustituto del archivo. El frontend puede previsualizar su archivo local; no
hay un endpoint adicional de lectura/edición de perfil en esta HU.

Alta válida: `201 {"status":"unverified","delivery":"pending"}`. No implica entrega SMTP
ni crea sesión. Error por campos: 400 con `details`; correo duplicado: 409
`email_already_registered`, sin cuenta/billetera extra. Ofrecer recuperación cuando HU-008
la implemente. Configuración/política/corpus ausente o no permitido: 503
`registration_unavailable`; mostrar indisponibilidad y conservar el formulario.

Errores siguen `{code, message, details}`. Los 429 usan `code=throttled` y cabecera
`Retry-After` en segundos; frontend debe esperar ese tiempo. No reintentar en bucle.
Un 403 `csrf_failed` requiere obtener CSRF y revisar cookie/origen. El permiso reutilizable
usa `email_not_verified`; no interpretar cualquier 403 como sesión vencida.

Para cada POST, incluso visitante, obtener `csrf_token` de `GET csrf/`, conservar cookie
`csrftoken` y enviar cabecera `X-CSRFToken`. Cookie de sesión HttpOnly y segura en
producción; se conservan sesiones Django sin JWT ni CORS universal. Las vistas públicas
llevan `csrf_protect`: SessionAuthentication sola no protege al visitante.

```javascript
const { csrf_token } = await fetch('/api/v1/auth/csrf/', {
  credentials: 'same-origin'
}).then(r => r.json());
const response = await fetch('/api/v1/auth/verify-email/', {
  method: 'POST', credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json', 'X-CSRFToken': csrf_token },
  body: JSON.stringify({ token })
});
```

## Estados, notificación y recuperación

Registro valida explícitamente los validadores Django y el corpus local. En una transacción
crea CLIENTE sin verificar, billetera cero sin fecha propia, consentimiento, notificación
y evento `registered`. La unicidad en PostgreSQL resuelve también dos registros simultáneos.
La imagen se escribe en almacenamiento privado; si falla persistencia, se revierte la base
y se elimina ese archivo. Un cierre abrupto del proceso puede dejar un archivo sin referencia;
integración debe revisar esos casos antes de cualquier limpieza. No se borran archivos ajenos.

`EmailVerification` es una outbox específica de HU-007. Un comando separado procesa
solamente trabajo confirmado; SMTP ocurre fuera de la transacción, sin depender de un
callback en memoria. `sent_at` significa aceptación por el backend de correo, no entrega
al buzón. Los fallos mantienen la cuenta sin verificar y registran `mail_failed` con un
código seguro, sin excepción SMTP ni datos personales. Éxito registra `mail_sent`.

Correo: `EMAIL_VERIFICATION_FRONTEND_URL#token=…`. La firma Django tiene propósito separado
y vincula cuenta y notificación; no contiene perfil ni correo y no se almacena el token
firmado. Vence a las **24 h desde que se crea esa notificación**, nunca desde un reintento.
Hay también restricción de vigencia en la base. Frontend extrae el fragmento, lo elimina
con `history.replaceState`, evita consola/analítica y pide confirmación explícita por POST.
GET no consume el enlace y los escáneres de correo que solo abren enlaces no verifican cuentas.

Confirmación bloquea usuario y notificación, comprueba destinatario vigente, cuenta activa
CLIENTE, vigencia y uso; cambia verificación y registra `verified` en una sola transacción.
200 `{"status":"verified"}`; inválido/alterado/otro propósito/cuenta/sustituido: 400
`verification_invalid`; vencido, incluido el instante exacto: 410 `verification_expired`;
consumido o cuenta ya verificada: 409 `verification_used`. Repetir no desverifica ni duplica
efectos; el estado consumido tiene prioridad sobre un vencimiento posterior.

Reenvío recibe `{"email":"persona@example.invalid"}`. Devuelve 202 `{"status":"requested"}`
para una solicitud admitida, también si la cuenta es desconocida, inactiva o verificada.
Solo para CLIENTE activo sin verificar crea nueva notificación de 24 h, marca anteriores
como sustituidas y registra `resent`; no crea usuario ni billetera. El enlace viejo deja
de servir. Si un correo viejo ya estaba en tránsito puede llegar después; frontend debe
indicar usar el más reciente. No se promete entrega SMTP exactamente una vez.

**DEC-16:** ventana móvil de 3600 s en PostgreSQL; registro 10 solicitudes por origen/hora;
reenvío 20/origen/hora y 5/correo/hora, con intervalo mínimo 60 s desde el envío inicial o
última solicitud admitida. El inicial inicia la espera sin consumir uno de los cinco
reenvíos. Origen se cuenta para solicitudes con CSRF válido, incluso inválidas después;
correo se cuenta tras validar su formato, incluso desconocido/verificado. Un rechazo por
correo también consume la cuota de origen. Las cuotas se reservan antes de la operación
y no se devuelven si falla persistencia. La respuesta normal es uniforme; no se promete
indistinguibilidad temporal, pues una cuenta recién creada ya tiene intervalo inicial.

`RegistrationRateBucket` conserva ventanas pequeñas bajo bloqueo y claves HMAC de ámbito
+ origen/correo, sin valores en claro. No usa memoria local. Procesos deben compartir
SECRET_KEY y PostgreSQL. Por defecto origen es `REMOTE_ADDR`. Solo si el peer está listado
en `REGISTRATION_TRUSTED_PROXIES` se utiliza `X-Real-IP`; un encabezado externo no basta.
Nginx de referencia sobrescribe esa cabecera. Integración debe limitar acceso directo a
Gunicorn y configurar el peer real; una lista incorrecta puede agrupar usuarios o aceptar
orígenes falsos. No se resolvieron límites de autenticación/confirmación u otras HU de P-05.

El procesador reclama con `skip_locked` y lease de 5 min. Reintenta el mismo trabajo a los
60, 120, 240… segundos, máximo una hora entre intentos, solo mientras esté vigente.
No confundir esto con un nuevo enlace solicitado por el usuario. Un lease abandonado
se recupera; dos procesos no reclaman simultáneamente la misma fila. Caer después de SMTP
y antes de guardar `sent_at` puede repetir el mensaje; el consumo sigue teniendo un único
efecto. Se omiten trabajos vencidos, sustituidos, consumidos o de cuentas inactivas/verificadas.

`RegistrationEvent` contiene cuenta, notificación, tipo y fecha: sin tokens, contraseñas,
excepciones, IP ni perfil replicado. No se añadieron CRUD de eventos ni otras historias.
`HasVerifiedEmail` exige cuenta autenticada, activa y verificada; futuras reservas/compras/
billetera deben combinarlo con rol y propiedad y probarlo en sus endpoints. HU-008 debe
permitir autenticación sin verificación; no existe login en esta entrega.

## Corpus local y almacenamiento

Pillow **13.0.0** es la única dependencia añadida, resuelta con Python 3.13.16 y hashes en
base/development/production; tools y las versiones existentes permanecen iguales.
Las imágenes viven bajo `PRIVATE_MEDIA_ROOT`, fuera de Git y del contexto Docker; no se
publican en `/media/`, no tienen URL pública ni se devuelven rutas internas. El Dockerfile
prepara directorios del usuario `app` y Compose conserva imágenes y corpus en volúmenes
nuevos `private_media` y `password_corpus`; el volumen PostgreSQL existente no se cambia.
El usuario confirmó la ejecución de HU-007 en Docker/PostgreSQL 17.11; ver evidencia
atribuida más abajo. Las pruebas operativas de imágenes persistentes, backups y corpus real
siguen siendo independientes de esa comprobación.

El lector del corpus busca un SHA-1 mediante búsqueda binaria sobre un archivo local
ordenado y de registros de 20 bytes, sin transmitir contraseñas ni usar SHA-1 para
almacenarlas (siguen con Argon2id). El importador acepta `SHA1:COUNT`, ordenado por hash y
sin duplicados; conserva manifiesto con etiqueta, cantidad, tipo sintético y SHA-256.
Rechaza vacío, datos inválidos o destino existente. El lector comprueba tamaño/integridad,
cachea la validación por identidad del archivo y usa mmap de solo lectura. No hay fallback
si falta o está corrupto. El corpus se despliega **inmutable**, por directorio versionado;
no editarlo durante consultas. La primera validación de cada proceso recorre el archivo:
integración debe medir y preparar los workers antes de habilitar tráfico con un corpus grande.

Integración debe obtener el corpus completo según la [fuente oficial de Pwned Passwords](https://haveibeenpwned.com/API/v3#DownloadingAllPwnedPasswordsHashes),
registrar procedencia/fecha y renovarlo mediante un directorio nuevo. El procedimiento
completo, estimación de espacio, descarga, transformación, checksums, montaje e importación
está en [HU-007_CORPUS_PWNED_PASSWORDS.md](HU-007_CORPUS_PWNED_PASSWORDS.md).
No se descargó el corpus real ni se presenta una muestra como lista completa. El corpus
sintético de las pruebas demuestra el mecanismo, no el aprovisionamiento productivo.
